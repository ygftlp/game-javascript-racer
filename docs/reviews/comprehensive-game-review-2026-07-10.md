审查角色：游戏策划、资深美术、客户端开发

## 1. 执行结论

当前项目已经从原始浏览器赛车 Demo 演进为具备微信小游戏入口、模块化运行时、多赛道、设置、排行榜适配层、移动摇杆和基础道具的可玩原型。

综合判断：

- 原型可玩度：6.5 / 10
- 移动操控基础：6.5 / 10
- 核心玩法深度：4.5 / 10
- 视觉完成度：4 / 10
- 工程稳定性：6 / 10
- 商业发布准备度：3 / 10

结论为 **Prototype Go / Commercial No-Go**。

在解决本报告 P0 问题前，不建议提交正式微信审核、投放买量或接入真实广告变现。

## 2. 已完成的即时工程治理

本轮审查期间已经落地以下安全改进：

1. `npm run build:wx` 和 `npm run build:wx:gamex` 构建前强制执行 TypeScript 类型检查和生产结构校验。
2. `npm run validate` 同时执行类型检查、资产校验和生产结构校验。
3. 新增 `.github/workflows/racer-ci.yml`，在分支推送和 PR 更新时执行：
   - 安装依赖
   - `npm run typecheck`
   - `npm run validate:production`
   - `npm run build:wx:gamex`
4. 保留当前 0.03 实际摇杆死区，同时兼容现有生产校验规则。

以上改动只能建立质量门禁，不能替代微信开发者工具和真机测试。

# 3. 游戏策划审查

## 3.1 当前核心循环

当前循环为：

1. 进入菜单。
2. 选择赛道和控制灵敏度。
3. 自动加速，通过摇杆转向和刹车躲避交通车辆。
4. 拾取加速、氮气或减速道具。
5. 完成目标圈数。
6. 记录最佳圈速、分享或查看排行榜。

优点：

- 进入比赛步骤短，适合微信小游戏碎片化场景。
- 三条赛道具备不同长度和弯道密度。
- 设置项能保存赛道、声音、雷达和灵敏度。
- 已存在最佳圈速、比赛结算和排行榜扩展点。
- 道具使原本单一的躲车循环开始产生节奏变化。

## 3.2 P0 玩法问题

### P0-GD-01：氮气没有形成玩家决策

当前氮气拾取后立即自动生效。玩家无法储存、选择直道释放或在落后时反击，因此氮气更像随机加速带，而不是赛车游戏中有策略价值的资源。

建议：

- 新增 0–100 氮气槽。
- 拾取氮气补充储量，而不是立即全部释放。
- 右下增加独立氮气按钮，按住消耗、松开停止。
- 氮气在弯道中提高失控风险，形成风险收益。
- 首版允许最大储存 2 次完整喷射。

验收：玩家可以主动选择氮气释放时机，且一次比赛至少产生 3 次有意义的释放决策。

### P0-GD-02：减速道具语义和公平性不足

当前“减速”与加速、氮气一样作为可拾取物放在赛道上。若视觉辨识不足，玩家容易把它理解为奖励却被惩罚。

建议二选一：

- 方案 A：明确改名为“油渍 / 路障 / 电磁陷阱”，使用危险形状、红黑配色和地面警示。
- 方案 B：改为玩家可使用的攻击道具，对前方 AI 车辆或排行榜幽灵生效。

首版推荐方案 A，开发成本更低。

验收：首次游玩的玩家在不读说明的情况下，能够从颜色和形状判断该物体应当躲避。

### P0-GD-03：道具生成没有安全和公平规则

当前道具按固定间隔和固定类型序列生成，没有检查：

- 是否生成在急弯盲区。
- 是否和交通车重叠。
- 是否连续生成多个惩罚物。
- 是否为玩家保留可通过车道。
- 不同赛道长度下的密度是否一致。

建议建立 `PowerupSpawnRule`：

- 起点后 5 秒内不生成惩罚物。
- 急弯入口前不生成氮气。
- 同一横截面至少保留一条安全车道。
- 道具与车辆保持最少 6–10 个 segment 的前后间隔。
- 连续两个减速陷阱之间至少间隔 12 秒车程。
- 根据赛道时长而非 segment 数量控制密度。

### P0-GD-04：缺少道具教学

当前首次比赛引导只说明摇杆和刹车，没有解释“加 / N / 减”的含义。

建议：

- 第一圈首次出现每种道具时显示一次 1.5 秒短提示。
- 操作说明页增加道具图例。
- 氮气改为手动后，首次获得时高亮氮气按钮。

## 3.3 P1 玩法问题

### P1-GD-01：没有中长期目标

只有最佳圈速不足以支撑留存。建议逐步增加：

- 三星赛道目标：完赛、低碰撞、目标时间。
- 每日挑战：指定赛道、指定车辆或无碰撞任务。
- 车辆外观解锁，不先做复杂性能养成。
- 连胜或连续无碰撞奖励。

### P1-GD-02：缺少比赛位置和对抗目标

当前交通车辆是障碍，不是真正对手。可先增加低成本目标：

- 幽灵车。
- 分段目标时间。
- “超过 X 辆车”任务。
- 赛道排行榜分开统计。

### P1-GD-03：碰撞惩罚缺少层次

目前碰撞主要直接限制速度。建议区分：

- 轻微擦碰：少量减速和短震动。
- 正面碰撞：显著减速、屏幕闪烁和 0.3 秒转向抑制。
- 路边障碍：根据物体大小产生不同惩罚。
- 0.35–0.5 秒碰撞保护，避免一帧内多次计数。

### P1-GD-04：数值全部硬编码

道具持续时间、速度倍率、复活时间和生成间距都写在状态类中。应提取到 `RacerPowerupConfig.ts`，便于策划调参和 A/B 测试。

# 4. 资深美术审查

## 4.1 当前视觉优点

- 已建立统一 UI Theme、程序化 Logo 和图标回退。
- HUD、菜单、设置、赛道选择和结算界面结构完整。
- 玩家车具有转向姿态和氮气尾焰反馈。
- 道具使用黄、蓝、红进行初步语义区分。
- 已有完整的商业美术和音频制作 brief，以及资产权利登记模板。

## 4.2 P0 美术问题

### P0-ART-01：运行时仍使用 legacy 资产包

当前活动资产包仍是 `LEGACY_RACER_ASSET_PACK`，并明确标记 `commercialSafe: false`。

商业发布前必须替换并批准：

- 背景图集。
- 玩家与交通车辆图集。
- 路边物体和广告牌。
- 背景音乐。
- 相关授权证明。

资产权利登记表中上述资源仍处于 `needed` 状态，因此属于正式发布阻断项。

### P0-ART-02：三条赛道缺少真正的视觉身份

三条赛道目前共用同一道路主题，差异主要来自弯道和 roadsideTheme 的随机物体选择。

建议每条赛道至少建立：

- 独立天空和地平线色板。
- 独立路面、路肩、雾色和标线。
- 独立路边物件池。
- 独立起终点门和赛道标识。
- 2–3 个强记忆点地标。

建议方向：

- 极速公路：暖色落日、郊外公路、黄色导向牌。
- 海岸冲刺：高明度蓝绿、海面和护栏、白色建筑。
- 城市夜跑：深蓝紫、霓虹灯、城市天际线和反光路面。

### P0-ART-03：道具视觉仍是开发占位

“加 / N / 减”旋转方块适合功能验证，不适合作为最终美术。

建议建立独立道具图集：

- 加速：黄色箭头或能量门，强调向前运动。
- 氮气：蓝色罐体或能量胶囊，带外发光。
- 减速陷阱：红黑危险地面贴花，不应漂浮成奖励形态。
- 拾取瞬间：缩放、粒子、闪光和声音同步。

### P0-ART-04：缺少商用音频闭环

代码已经接入音乐、引擎、碰撞和菜单确认音效，但商用资产均未提供或未批准。

道具还需要新增：

- 加速拾取音。
- 氮气启动和持续喷射音。
- 减速陷阱命中音。
- 氮气耗尽提示音。

## 4.3 P1 美术问题

### P1-ART-01：车辆和道路可读性需要真机验证

必须在低亮度、低分辨率和高 DPI 手机上检查：

- 玩家车是否从道路中分离。
- 交通车在碰撞距离前是否可辨认。
- 山坡和弯道是否遮挡道具。
- 雾效是否降低危险物识别。
- HUD 是否遮挡赛道信息。

### P1-ART-02：UI 语言风格不统一

当前界面同时存在中文、`mph`、英文内部状态和程序化英文标签。正式版应统一：

- 中文界面建议显示 `km/h` 或仅显示整数速度。
- “STEER”等英文控制标签应移除或本地化。
- 调试状态不能进入发布版本。

### P1-ART-03：缺少碰撞和速度感特效

建议优先添加低成本 Canvas 特效：

- 氮气屏幕边缘速度线。
- 轻碰火花。
- 正面碰撞白闪或红闪。
- 高速轻微镜头震动。
- 加速时 FOV 或道路拉伸的轻量反馈。

# 5. 客户端开发审查

## 5.1 当前工程优点

- TypeScript 模块边界已基本建立。
- 微信平台、服务、资源、状态、渲染和 UI 已分层。
- 存在本地兼容引擎和外部 lite-game-engine 接入模式。
- 分辨率和性能档位有基础自适应。
- 资源加载失败时有程序化回退。
- 微信分享、广告、排行榜和分析均通过适配层隔离。
- 构建前现已加入类型检查和生产校验。

## 5.2 P0 工程问题

### P0-DEV-01：新道具 HUD 使用 `ctx.roundRect`

部分微信 Canvas 环境对 `CanvasRenderingContext2D.roundRect` 支持不一致，而项目其他 UI 已刻意使用手写圆角路径兼容。

建议：

- 将 `Pseudo3DRenderer.drawPowerupFeedback()` 中的 `ctx.roundRect` 替换为本地 `roundedRectPath()`。
- 在生产校验中禁止所有运行时代码使用 `.roundRect`，而不只检查 Logo 和 Icon 文件。

### P0-DEV-02：双指抬起后的输入状态不可靠

当前场景的 `handleTouchEnd()` 会重置全部控制。玩家同时使用左侧摇杆和右侧刹车时，抬起其中一根手指可能导致另一根仍按住的手指失效。

浏览器兼容引擎的 `touchend` 还传入 `changedTouches`，而不是剩余 `touches`。

建议：

1. 引擎层 `touchend` 统一传递仍在屏幕上的触点。
2. 场景层若仍有触点，则重新执行 `applyTouches(remainingTouches)`。
3. 为摇杆绑定固定 touch id，直到对应触点结束。
4. 真机验证摇杆 + 刹车、摇杆 + 氮气、三指异常输入。

### P0-DEV-03：高速和低帧率下可能漏拾道具

当前碰撞只检查单个 `playerSegment`。氮气最高速度超过基础上限，在 30 FPS 或卡顿帧中，赛车单帧可能跨过一个以上 segment，导致道具或车辆碰撞漏判。

建议：

- 使用上一帧和当前帧位置做 swept segment 检查。
- 对跨越的所有 segment 执行一次碰撞检测。
- 对 `dt` 做最大值限制，例如 1 / 20 秒，并将超长帧拆成多个 physics step。

### P0-DEV-04：长期 PR 体积过大且不可合并

当前 PR 已累计数百个提交和超过百个变更文件，并处于 `mergeable: false` 状态。

风险：

- 很难做有效代码评审。
- 与 `master` 冲突概率高。
- 任一回归难以定位。
- 合并和回滚成本过高。

建议：

- 从最新 `master` 建立干净集成分支。
- 按“微信运行时 / UI / 商业资产 / 道具玩法 / 平台服务”拆成多个可审查 PR。
- 每个 PR 控制在一个明确目标和可独立验证范围内。

### P0-DEV-05：发布配置仍是开发模板

`project.config.json` 仍使用 `touristappid` 且关闭 `urlCheck`。正式发布前必须使用真实 AppID、恢复合规配置并在微信后台验证域名和隐私要求。

## 5.3 P1 工程问题

### P1-DEV-01：Powerup 逻辑集中在 `RacerState`

当前 `RacerState` 同时负责：

- 赛道生成。
- 车辆交通。
- 碰撞。
- 道具生成。
- 道具计时。
- 道具效果。
- 圈速。

建议拆分：

- `RacerPowerupConfig.ts`
- `RacerPowerupSystem.ts`
- `RacerCollisionSystem.ts`
- `RacerRaceProgress.ts`

状态类只保存数据并协调系统。

### P1-DEV-02：缺少自动化测试

建议最低覆盖：

- 摇杆死区和响应曲线。
- 三档灵敏度。
- 道具持续时间和速度上限。
- 道具复活。
- 低帧率跨 segment 拾取。
- 圈数和赛道切换。
- 设置和最佳圈速存储。

### P1-DEV-03：CI 缺少锁文件

当前没有 `package-lock.json`。CI 使用 `npm install`，依赖版本可能随时间漂移。

建议在依赖确认后提交锁文件，并将 CI 改为 `npm ci`。

### P1-DEV-04：道具缺少分析事件

建议新增：

- `powerup_spawn`
- `powerup_pickup`
- `powerup_avoid`
- `nitro_start`
- `nitro_end`
- `slow_hit`

用于判断道具是否被识别、是否公平以及是否改善比赛节奏。

### P1-DEV-05：生产校验过度依赖字符串 token

当前生产校验通过查找源码字符串判断功能是否存在，重构变量名就可能误报。

建议：

- 结构检查保留文件存在性。
- 行为检查迁移到 TypeScript 单元测试。
- 构建和运行冒烟使用实际入口。
- 商业资产使用 JSON Schema 或结构化 manifest 校验。

# 7. 建议实施节奏

## Sprint A：稳定可玩版本

目标：操控、碰撞和道具在真机上稳定。

范围：

- P0-DEV-01 至 P0-DEV-03。
- 道具生成公平规则。
- 减速陷阱视觉调整。
- 道具首次教学。
- 3 台 Android + 2 台 iOS 微信真机测试。

退出条件：

- 连续玩 10 局无输入卡死。
- 30 FPS 压测不漏拾主要道具。
- 无不可躲避道具和车辆组合。
- CI 全绿。

## Sprint B：玩法完成版本

目标：道具产生明确策略和复玩动机。

范围：

- 氮气槽和手动释放。
- 道具平衡配置化。
- 圈速目标、三星评价或每日挑战。
- 关键分析事件。

退出条件：

- 新玩家首局完成率可统计。
- 每局平均产生至少 3 次有意义道具决策。
- 三种灵敏度均通过真机测试。

## Sprint C：商业美术和发布版本

目标：替换全部高风险资产并完成微信发布配置。

范围：

- 商用背景、车辆、赛道和声音。
- 三赛道独立主题。
- 真实 AppID、排行榜、分享、广告和隐私配置。
- 权利证明和发布清单。

退出条件：

- 活动资产包切换为 commercial template。
- 所有 P0 资产标记 `approved`。
- 微信审核包不含 legacy-risk 资源。
- 发布负责人完成 Go / No-Go 签字。

# 8. 必须执行的真机测试矩阵

分辨率：

- 568 × 320
- 667 × 375
- 812 × 375
- 896 × 414
- 1280 × 720

场景：

- 单指摇杆。
- 摇杆 + 刹车双指。
- 摇杆 + 氮气双指。
- 双指抬起顺序互换。
- 来电 / 切后台 / 恢复。
- 低电量和性能降频。
